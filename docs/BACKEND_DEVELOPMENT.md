# Backend and Agent development

The repository is an npm workspace with three processes:

- `apps/web`: the bedroom editor and furniture review client;
- `apps/api`: Fastify JSON/SSE control plane;
- `apps/agent-worker`: pg-boss consumer and trusted Codex runner.

Shared contracts live in `packages/contracts`; PostgreSQL schema and migrations in `packages/database`; immutable object drivers in `packages/storage`; API client adapters in `packages/bedroom-core`; furniture contract validation in `packages/furniture-assets`.

## Local start

Use Node.js 22 or newer. Copy `.env.example` into an ignored local environment file and load it into the shell. Create the PostgreSQL database, then apply the SQL migration under `packages/database/migrations`. Use a dedicated database role rather than a PostgreSQL superuser.

Run processes separately while debugging:

```text
npm run dev:web
npm run dev:api
npm run dev:worker
```

Or run `npm run dev:all` after setting `DATABASE_URL`, `AGENT_WORKER_TOKEN`, `AGENT_WORKSPACE_ROOT`, and `AGENT_REPOSITORY_ROOT`.

The browser defaults to `127.0.0.1:5555`; the API defaults to `127.0.0.1:3333`. Origins are an exact comma-separated allowlist. Do not use `*` with authenticated requests.

## Storage

`filesystem` requires an absolute `STORAGE_ROOT`; traversal segments are rejected. Layout keys are generated by the API. Asset revision references are accepted only when the object already exists below `tenants/{tenantId}/assets/{assetId}/`; the upload-init route that will generate these keys for untrusted clients remains a Phase-G task. Writes are immutable and accompanied by SHA-256, byte count, and MIME metadata. The S3 driver keeps buckets private and can create short-lived signed URLs. The API database stores keys and hashes, not GLB/image/source bytes.

## Identity and isolation

`AUTH_MODE=development` exists only for local work and accepts explicit development identity headers. Production must use `AUTH_MODE=oidc` with issuer, audience, and JWKS URL. Every repository query constrains tenant and workspace IDs.

Public clients never call Codex or pg-boss. They create a run, then consume `/events` with SSE. Events have a durable sequence; `Last-Event-ID` replays missing records before live events. The internal Worker update endpoint requires a capability token and is not routed by the supplied Caddy configuration.

`AGENT_EXECUTION_MODE=mock` validates control-plane behavior without model calls. `app-server` mode follows the official Codex App Server stdio JSONL handshake and creates a detached Git worktree per run. It is restricted to trusted administrator repository tasks. Phase-H isolation is still required before executing ordinary-user JS/TS.

## Status boundaries

Agent run state and asset state are independent. Asset revisions store both raw and effective status. Revision creation rejects a direct `approved` claim and validates the manifest v3 contract; candidate creation additionally validates current contract-hash evidence. Only an effective candidate can pass the separate approval endpoint against its current hash.

## Production gates not completed locally

The repository contains adapters and deployment templates, not a live production installation. Before enabling external users, run integration tests against the selected PostgreSQL, private S3 service and OIDC provider; implement upload-init/quota/audit enforcement; exercise backup restoration; verify cross-process cancellation and dead-run recovery; and complete the Phase-H isolated runner. Do not expose arbitrary user JS/TS to the current trusted-process Worker.
